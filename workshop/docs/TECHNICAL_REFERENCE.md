# Personal Journal 1.02 Technical Reference

本文档描述当前已发布版本。适用范围：Project Zomboid
Build 42.20，Workshop `3788037313`，Mod ID `LegacyJournal`，公开版本
`1.02`，物品数据格式 `LJ_version=6`，内部构建标识
`20260831-page-rate7of1000-localized-job-item-write-tooltip-guard-5`。

## 1. 最高实现原则

能由原版物品、TimedAction、玩家状态、物品 `modData`、字段同步和玩家字段同步
表达的行为，优先复用原版。自建逻辑只负责以下原版没有的能力：

- 日志作者与账号继承边界；
- 知识快照、差值与确定性恢复；
- 动态页数和中断续作；
- 多人游戏的服务端权威事务协议；
- 本地化名称与记录时间的展示。

TimedAction 的物品栏 `jobType` 对首次写空日志只保存本地化动作文本；对已经写完并改名的
日志，使用与原版物品栏一致的 `item:getName(character)` 保留当前自定义显示名。不得调用
无人物参数的 `item:getName()`，避免动作期间泄露内部英文名称。物品持久显示名仍由表现模块
独立刷新。

本项目仅面向 B42.20，沙盒翻译只使用 `Translate/<locale>/Sandbox.json`。旧式
`Sandbox_<locale>.txt` 已删除，避免同一选项存在两套不一致文本；门禁同时校验三语 JSON
页面名、选项名和 tooltip 键。

Mod 自定义 ContextMenu 文本只保留“写日志”和一个通用“无法写入”说明。作者不符、缺少
书写工具、没有新内容三种写入禁用状态共用该说明；禁止阅读使用原版
`ContextMenu_EmptyNotebook`，光线与文盲限制也继续使用原版键。
该写入说明固定为简中“无内容可写”、繁中“無內容可寫”、英文“Nothing to write”。

仅支持原版 `Base.Diary1` 和 `Base.Diary2`。不新增物品、配方或依赖，移除
Mod 后物品仍是原版日记本。

## 2. 模块职责

| 模块 | 职责 |
| --- | --- |
| `legacyjournal_shared.lua` | 数据编码、身份、快照、差值、页数、续作、写入与恢复 |
| `legacyjournal_actions.lua` | 原版风格的读写 TimedAction、动画、进度条和整页检查点 |
| `legacyjournal_client.lua` | 右键菜单、物品转移、多人请求、客户端字段补充同步 |
| `legacyjournal_server.lua` | 服务端验证、一次性令牌、检查点、提交和原生同步 |
| `legacyjournal_presentation.lua` | 可见容器中的本地化名称刷新，不反向同步数据 |
| `legacyjournal_skillbook_compat.lua` | 即时动作下原版技能书页数兼容 |

单人游戏直接在本地执行相同的共享差值、页数、写入和恢复函数。多人游戏仅由
服务端执行最终数据变更。

## 3. 持久化数据

日志主体字段保存在实体日记本的 `modData`：

- `LJ_written`：是否已成为个人日志；
- `LJ_version`：精确数据格式版本，当前为 `6`；
- `LJ_authorName`、`LJ_authorUser`、`LJ_authorDescId`：展示名、账号名和角色描述符；
- `LJ_writtenAt`：最近一次成功写入的游戏内时间；
- `LJ_skills`：技能 ID 到历史 XP；
- `LJ_recipes`：已知配方集合；
- `LJ_skillBooks`：技能书完整类型到已读页数；
- `LJ_skillBookStates`：技能书的技能 ID、倍率和有效等级区间；
- `LJ_mediaRewards`：稳定媒体 ID 到已知媒体类型掩码；
- `LJ_mediaRewardMode`：当前为 `whole-media`。

续作字段为 `LJ_progressAction`、`LJ_progressSignature`、
`LJ_progressActor`、`LJ_progressPage`、`LJ_progressTotalPages` 和
`LJ_progressModelVersion`。最后一个字段只标识临时续作页数模型，不改变知识 schema。

技能与页数使用排序后的 `key=value;...`；配方使用排序后的换行集合；技能书
状态使用稳定 TSV 字段。排序用于保证快照签名和恢复选择可重复。

只接受精确 v6。`migrateRecord` 当前只是精确版本判定，不会猜测迁移或覆盖
无版本、旧版、损坏版和未来版本。升级公开版本不等于升级物品数据格式。

## 4. 记录与恢复语义

### 技能 XP

写入保存每项技能见过的最高 XP。恢复目标为
`saved XP * RecoveryPercent`，以 `0.001 XP` 精度比较和写入。只补足缺失值，
不会降低当前角色已有 XP。

### 配方、技能书与培训媒体

恢复比例不是随机抽取。每个类别按稳定标识排序，固定选择
`ceil(记录数量 * 恢复比例)` 项。重复阅读同一本日志不会换一批项目，也不会
逐次刷到 100%。

技能书写入保存原版 `getAlreadyReadPages` 和可观察的实际倍率/等级区间。可观察
的较低新快照允许覆盖旧快照；枚举失败、书籍 Mod 暂时缺失或倍率不可观察时保留
旧值。恢复仅提高页数和倍率，只处理当前等级适用的书籍区间；文盲角色不恢复。

培训媒体枚举 CD 类型 `0` 和 VHS 类型 `1`。一个媒体只要包含永久技能、XP 或
配方奖励行，就按稳定媒体 ID 记录整个媒体；恢复时补齐该媒体的全部行。纯娱乐
媒体不记录，混合媒体中的娱乐行会随整段媒体状态一并恢复。

### v6 旧日志的技能书基线补写

部分早期 v6 日志没有 `LJ_skillBookStates` 精确快照。当前代码仍把它视为 v6，
因此可能在角色没有明显变化时开放一次写入，用于补齐技能书状态基线。成功写入
后字段齐全，后续无变化时菜单应禁用。这是同版本兼容行为，不是普通的重复写入。

## 5. 动态页数与时间

只有存在可写或可读差值时动作才会开始。差值先换算为内容单位：

```text
writeUnits = 600
           + changedSkills * 120
           + ceil(XP / 100) * 1
           + newRecipes * 90
           + changedSkillBooks * 100
           + mediaLines * 8

readUnits  = 900
           + changedSkills * 90
           + ceil(XP / 100) * 0.8
           + missingRecipes * 75
           + missingSkillBooks * 85
           + missingMediaLines * 6

pages = max(1, ceil(units * 7 / 1000))
```

1.01 的等价公式是 `ceil(units * 10 / 1000)`；1.02 直接把原公式的页数累计率从
每 1000 内容单位 10 页改为 7 页，只在最终取整一次，不先计算旧整数页数再乘 0.70。
因此 100000 内容单位严格从 1000 页变成 700 页。页数没有人为上限。动作基础时间复用
Build 42 的原版读书关系：

```text
maxTime = pages * MinutesPerPage * MinutesPerDay * 2
```

之后应用沙盒读写时间倍率。阅读还保留原版快读/慢读、阅读眼镜和坐地修正；
写入不伪装成技能书阅读，因此不套用阅读特质。

## 6. 中断续读与续写

历史进度和当前事务使用不同的约束：

- 历史检查点要求同一实体日志、同一动作类型和同一 `actorKey`；
- `actorKey` 由 username、角色 descriptor ID 和人物名组成，因此另一角色不能
  继承未完成动作；
- 1.01 无模型版本的旧检查点首次读取时按 `oldPage / oldTotalPages` 映射到新总页数并向下
  取整，例如 `500/1000 -> 350/700`；未知的显式未来模型不猜测，按无续作处理；
- 1.02 同模型内，知识状态或总页数在两次动作之间发生变化时，已完成绝对页数继续保留，
  并截断到新总页数；
- 客户端只在跨过整页时提交检查点；
- 服务端用最大值合并检查点，较小或重复页码不能使进度倒退；
- 当前动作的一次性令牌仍绑定开始时的完整知识签名；动作进行中状态变化时，旧
  令牌不能提交，必须重新开始事务；
- 新检查点写入模型版本；成功写入或恢复后连同其他续作字段一起清空。

这解决了“多次中断期间自然获得 XP，签名变化后从第一页重来”的问题，同时不
允许一个旧令牌把已经变化的状态当作原快照提交。

## 7. 多人事务协议

客户端上行只包含意图和进度：

- `begin(action, itemId)`；
- `checkpoint/cancel(action, itemId, token, page)`；
- `commit(action, itemId, token)`。

客户端不上传 XP、配方、技能书或媒体快照。服务端流程：

1. 在玩家递归背包内重新找到物品；
2. 验证原版日记本类型、精确数据版本、作者、书写工具和非空差值；
3. 自行计算签名、页数、时间和续作页，发放一次性令牌；
4. 接受与玩家、物品、动作和令牌匹配的单调页检查点；
5. 提交时先消费令牌，再重新查物品、重算差值和签名；
6. 验证通过后由服务端调用 `commitWrite` 或 `applyRead`；
7. 使用原生 `syncItemFields` 和玩家字段同步发送最终状态。

每名玩家同时只允许一个待提交动作。令牌最长保留两小时现实时间，断线事件会
清理内存中的待提交动作。配方与媒体下行每批最多 50 项，技能书状态在最终批次
发送。

作者授权优先绑定服务端认证 username，因此同一服务器账号的新角色可以读取和
更新日志。早期记录缺少作者 username，或运行环境无法取得 username 时，代码会
回退到人物显示名。这是兼容路径，不应被描述为与 username 同等强度的权限边界。

## 8. 客户端显示与同步陷阱

服务端写入后，客户端只本地刷新本地化名称和提示。客户端绝不能再次调用
`syncItemFields`，否则可能把写入前的旧 `modData` 反向覆盖服务端结果。

多人客户端不能可靠观察技能书 XP multiplier，因此仅有倍率差异不能单独开放
阅读菜单。服务端恢复后再下发确定字段，客户端按原版路径补齐页数与倍率。

Build 42 的堆叠菜单包含 dummy 项。菜单必须使用
`ISInventoryPane.getActualUniqueItems` 取得每个 UI 堆叠的真实代表项，不能把
dummy 或整组项目展开成重复命令。地面和容器中的日记本先走原版
`transferIfNeeded`，确认进入玩家递归背包后再发送 `begin`。

## 9. 已知边界

- 服务端权威保护数据内容，但不把耗时作为防作弊边界。当前提交会校验令牌和
  状态签名，不会验证已耗现实时间或必须到达最后一页；修改客户端可能跳过等待。
- `begin` 回包丢失时，客户端 `pendingBegins` 没有独立超时。极端网络故障可能
  需要重连，服务端待办最长两小时后清理。
- username 缺失时的人物名回退属于旧记录兼容，不适合作为高对抗服务器的强身份
  认证。

以上边界不阻止当前版本冷维护，但若出现真实滥用、卡死或数据错误，应按冷维护
触发条件重新开修复版本。

## 10. 测试与发布

`run_offline_tests.ps1` 使用固定版本的 Lua 解析器检查 6 个 Lua 文件，并运行
12 个 Fengari 行为测试。覆盖技能书、培训媒体、服务端令牌、重放/错物品/过期、
客户端检查点、动态页数、跨签名续作、堆叠菜单、无变化差值和恢复路径。

`validate_workshop.ps1` 验证 Workshop 结构、版本、翻译、禁止项、协议关键路径和
安装器回读。公开仓库的自动化与人工验收范围见根目录 `docs/TESTING.md`；服务器
地址、发布凭据和内部运维流程不属于公开仓库。

## 11. 冷维护规则

当前 1.02 进入发布后维护，并且是用户指定的当前唯一认可回滚基准；1.01 只作为上个版本保留。
除以下情况外不继续功能开发：

- Project Zomboid 更新造成可复现不兼容；
- 出现可复现的数据丢失、错误恢复、多人同步或权限问题；
- Workshop、客户端和服务器内容发生版本漂移；
- 用户明确开启新的版本目标。

修复必须从当前公开 1.02 的 23 文件认可基线建立隔离候选，同时保留 1.01 上个版本，
先离线验证，再使用独立多人档测试，最后经授权发布。不得直接在正式服运行副本上开发或热改。
